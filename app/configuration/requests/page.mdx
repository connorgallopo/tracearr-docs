# Seerr Requests

Tracearr can link one **Seerr** instance to each media server. Overseerr and Jellyseerr share the same API, so any of the three works. Once linked, Tracearr mirrors the request history into its own database and shows it in three places:

- **Media detail** gets a line under the availability list, "Requested by agelwarg · Sep 8, 2026 · landed 2 min later", plus a Requests panel listing every request for that title.
- **User detail** gets a Requests card with a summary (requests, approval rate, never watched, median wait) and the person's request history, each row marked with whether they have watched what they asked for.
- **Requests** in the sidebar covers the servers you have picked: how many requests landed and got watched, what landed and was never played, and who follows through. See [The Requests page](#the-requests-page).

tofa and Silo servers have requests built in, so they need no Seerr; see [tofa requests](#tofa-requests) and [Silo requests](#silo-requests).

Tracearr only reads from Seerr, tofa and Silo. It never approves, declines or creates requests.

## Link a server

Go to **Settings → Servers → Connections**. Each server row carries a Requests line.

<Steps>

### Copy the API key from Seerr

In Seerr, open **Settings → General** and copy the **API key**.

### Link the server

Click **Link Seerr** on the server's row, paste the Seerr URL (the address you open Seerr at, without `/api/v1`) and the key, then click **Test** at the end of the key field.

### Check the match

A successful test names the Seerr instance, its version, its media server type, and the Tracearr server it belongs to. **Save** only enables when that server is the row you clicked. When editing an existing link, changing the URL with the key field left blank skips the test in the dialog; Tracearr re-checks the match on the server with the stored key and refuses the change if it points at a different media server.

</Steps>

A Seerr instance is bound to exactly one media server in its own settings. Tracearr compares the machine id Seerr reports against the server's own id, so a Seerr pointed at a different Plex or Jellyfin cannot be linked to the wrong row. The test result says which server it does match, if any.

<Callout type="info">
  Saving starts a full sync of the request history. On a Seerr with a few hundred requests that
  takes seconds; the row shows the request count once it lands. After that Tracearr checks Seerr
  every 15 minutes and does a full pass nightly. **Sync requests now** in the row's menu forces a
  full pass.
</Callout>

The API key is encrypted in the database the same way notification destination secrets are, under `ENCRYPTION_KEY` or, when that is not set, a key derived from `JWT_SECRET`. If that secret changes, the row shows **Needs API key** and sync pauses until you enter the key again.

## tofa requests

A tofa server keeps its own requests, and Tracearr reads them through the server's existing connection. Nothing needs linking: the server's row in **Settings → Servers → Connections** shows a Requests line from the moment the server is added, with the time of the last sync and the request count. The row's menu has no Seerr items for it, and a tofa server can't be linked to Seerr.

tofa lists every request in one answer and keeps no record of one it deleted, so each sync, every 15 minutes and nightly, reads them all and marks any that are gone as removed.

When requests are turned off in tofa, the row shows **Sync failed** with "Requests are turned off on this server", and syncing stops picking up new ones until they are turned back on. While no server takes requests, **Requests** leaves the sidebar.

## Silo requests

A Silo server's requests work the same way as tofa's. Tracearr reads them through the server's existing connection, the server's row shows a Requests line from the moment it is added, and a Silo server can't be linked to Seerr.

Each sync, every 15 minutes and nightly, reads every request Silo lists. Silo keeps a request someone cancelled, but Tracearr marks it as removed, along with any request Silo no longer lists. A request Silo made from a watchlist carries the watchlist flag.

When requests are turned off in Silo, the row shows **Sync failed** with "Requests are turned off on this server". Requests already in Tracearr stay, and the next sync after they are turned back on picks up new ones.

## How requests are matched

Each Seerr request carries the requester's plex.tv account id (Plex) or their Jellyfin or Emby user id, and the title's TMDB and TVDB ids. A tofa request carries the requester's tofa user id and the same two ids, and a Silo request the requester's Silo user id and the same two ids. Tracearr matches:

| Seerr field                          | Tracearr side                                 |
| ------------------------------------ | --------------------------------------------- |
| Requester's Plex account id          | The user's account on the linked Plex server  |
| Requester's Jellyfin or Emby user id | The user's account on the linked server       |
| Requester's tofa user id             | The user's account on that tofa server        |
| Requester's Silo user id             | The user's account on that Silo server        |
| TMDB id (movies), TVDB id (shows)    | The library title, across every copy you have |
| Plex rating key or Jellyfin item id  | Fallback when the provider ids do not match   |

No matching by username or email, and Seerr email addresses are never stored.

A Silo request also names the profile that asked. A profile other than the account's main one shows on the requester's avatar, as in History; see [What are profiles?](/faq#what-are-profiles).

The server row shows the request count. It does not show how many titles or users went unmatched. A title stays unmatched when it never arrived in the library or was removed later; the request still appears on the requester's user page with the title Seerr knows it by. A user stays unmatched when the requester has no account on the linked server, which is normal for Seerr local accounts. Those requests show the Seerr username in grey, or "Not on this server" when Seerr gave none.

Matching runs again on every full sync, so a title that arrives in the library after the request was mirrored links up on the next nightly pass. The 15-minute check only re-matches requests Seerr changed since the last run.

Seerr marks a title available only when it finds it in a library enabled under Seerr's own Plex or Jellyfin settings. A request whose title sits in a library Seerr does not scan stays approved in Seerr, and Tracearr shows it that way with no wait time, even though the title is in the Tracearr library.

## What the pages show

**Status** follows Seerr's own vocabulary: Pending, Approved, Declined, Failed, and Available (Seerr calls this completed). A request Seerr has since deleted stays in Tracearr with a Removed badge, so history survives cleanup in Seerr.

**Wait** is the time from the request to the title landing in the library. For a new season of a show already on the server, Seerr only records the moment it noticed the season was available, so the wait can be a few minutes longer than it really was.

**Seasons** lists the seasons a show request asked for, or All seasons. A 4K request and a request Seerr made from a watchlist each carry a small flag.

**Watched** uses the same rule as the rest of the library pages: a movie counts once it has been watched, a show counts once every episode currently in the library has, with a partial ring for progress. A show request that named seasons only counts those seasons, so a season 2 request is watched when season 2 is, whatever happened to season 1.

The badge has two colours. Green, "Watched by the requester", means the person who asked for it watched it. Orange, "Watched by someone else", means another account did and the requester has not. Green wins when both are true.

**Never watched** in the user summary counts available requests the requester has not started. It scans the 500 most recent available requests, so for a requester past that mark the figure is a floor.

## The Requests page

**Requests** appears in the sidebar once at least one server has Seerr linked or is a tofa or Silo server taking requests. It follows the server picker at the top of the app, so picking one server narrows every number on it. With nothing linked the page says "No Seerr linked" and offers **Link Seerr**.

Three cards run across the top:

| Card         | What it counts                                                           |
| ------------ | ------------------------------------------------------------------------ |
| Requested    | Every request, with how many of them landed underneath                   |
| Watched      | Requests that landed and got watched, as a share of the ones that landed |
| Never played | Requests that landed and nobody has played, with their size on disk      |

**Where requests end up** draws the same three stages as a funnel: Requested, Landed, Watched. "Watched means someone got through 85% of it, the same bar the library pages use. A request has to land and be matched to a title before Tracearr can measure that."

The funnel and the Requesters table judge a request by everything that landed for it, including episodes deleted since. Pruning a watched title never turns its request back into an unwatched one, and a season whose unwatched episodes were deleted stays unwatched here even when its poster badge reads watched.

**Landed and never played** lists the requests behind the Never played card, "Downloaded because someone asked, and no account on these servers has pressed play even once." It is zero plays from anyone, not under 85%, so a half-watched title never shows up here. It sorts largest on disk first, and a title with nothing on disk is left out.

**Requesters** has one row per person: how many titles they asked for, how many landed, how many they watched, how many someone else watched, and their median wait. It sorts by Watched first. For a show request that named seasons, only those seasons count towards watched.

## Unlinking

**Unlink Seerr** in the server row's menu deletes the mirrored request history for that server. **Pause request sync** in the same menu keeps the history and stops syncing; the row reads Paused until you choose **Resume request sync**. A tofa or Silo server's requests can be paused the same way but not unlinked; they go when the server is removed.

<Callout type="info">
  Linking Seerr does not add anything to automations or notifications. Request events as automation
  triggers are planned as a follow-up.
</Callout>
